# シフト・希望の提出と管理

従業員: 記録→「シフト・希望の提出」。管理者: 管理→「シフト作成・希望の確認」。初版の認証は既存LINE、同じTLHアカウント/従業員情報を使います。従業員へGoogle Sheetsを共有する必要はありません。

## 初めて月のシフトを作る

1. 管理者が月を選び、初回希望の締切を日本時間で設定します。固定で毎月何日と決めつけません。
2. 従業員は本人の画面で日付・希望区分・休暇や勤務・特記事項・理由を提出します。提出は確定ではありません。希望理由/個別メモ/用事の詳細は本人と管理者だけです。
3. 管理者は希望を確認し、承認して下書きへ反映、または理由を付けて見送りを記録できます。本人は未処理の自分の申請を取り消せます。
4. 管理者は社員番号（氏名）と日を選び、勤務区間・予定休憩・休暇・用事を下書き保存します。中抜けは区間を分け、翌日退勤を明示します。空白を休日/0時間へ変換しません。
5. 締切後に内容を確認して「下書きを全員へ確定公開」。全員向けには確定した時間帯/休暇の表示と、共有イベントを返します。個別理由や用事の名称/場所は共有しません。

月暦は月末と曜日を計算。祝日名や営業上のイベントは管理者が手入力します。自動で祝日や祭りを選ぶ機能ではありません。イベントは日ごと1つの名称/補足欄へまとめて入力し、確定後も更新できます。

## 確定後の変更

従業員からは初回締切に関係なく変更申請できます。管理者が承認するまでは確定シフトを変えません。管理者が既存予定を編集した場合は、直接上書きせず本人への変更案になります。本人がその内容へ同意→管理者が最終承認の順で反映します。同意なしの案を承認するボタンは出しません。

他の更新で対象版が変わっていた場合は再確認します。本人同意を別の変更案へ使い回しません。申請/同意/判断と公開履歴は削除せず版で残します。

## 休暇・勤務算入・実績との境界

通常の希望締切と、年休等の制度上の申出を分けます。初版の休暇入力は全日。有給を選んだ申出は通常希望の締切で拒否せず年休の区分で扱い、管理者が内容を確認します。有給残数の引去り、時間単位休暇の運用、給与・法定時間外の計算が完成したという意味ではありません。

会社が指示・拘束する用事は勤務対象から外せません。算入外の分類が未確認の用事は下書き保存できますが、予定実働を確定して全員公開することはできません。予定休憩を会議の重なりで自動的に減らしません。

シフトは予定、打刻は実績です。新シフトは専用カレンダーで閲覧します。旧「日別勤務とシフト」の予定差は従来のShiftPlanによるもので、新しい複数区間予定へ自動移行した表示ではありません。月次の本社提出は実績のみで、シフト未設定でも出力できます。

## 保存・失敗時・自分で改造する

GitHub main→既存GAS→既存シフト専用Sheetの順。共通Account/原打刻を複製せず、専用表のemployee_idが既存従業員へ対応します。保存先名は「TLH｜シフト・希望休・変更申請」。ファイル名は目印、接続はprivate設定のIDとpurpose/ヘッダーで検証します。

保存は追記した版と内容hash、操作者、日時、操作IDを持ちます。全員向け公開は全件の複製とhashの一致を確認します。途中保存を一部だけ公開しません。保存失敗は追加した行だけを補償し、補償を確認できなければシフト専用の要確認フラグで停止します。打刻の原簿や共通アカウントの停止フラグとは分けています。

結果不明は自動再送しません。「同じ操作で保存結果を再確認」は同じ内容/操作IDで確認します。最新状態の更新と、別内容での新しい保存を混同しないでください。画面を離れると秘密と申請入力を消し、履歴から戻った画面は新しい本人確認から再開します。
