# デザインの考え方と魔改造ガイド

## 現行パレットと管理・その他の統一（2026-11-03）

所有者が渡した6色を役割に割り当てました。色を変える入口はapp.cssの:root、管理/その他の配置は同ファイル18節です。

| 色 | 役割 |
|---|---|
| `#F3EFE7` | アイボリーの画面背景 |
| `#2F5452` | 主操作・リンク・見出し番号 |
| `#7C908E` | 入力枠・補足の目印。薄いため小さい本文には使わない |
| `#252829` | 本文と見出し |
| `#495C63` | 読める濃さを残す補足文 |
| `#8E3F35` | 利用停止・招待取消し・注意 |

字体はIBM Plex Sans JP、本文400・見出し/操作600に統一。数字/英字/日本語を同じファミリーへまとめ、入力欄も継承します。[フォントの保存先・ライセンス・再現](fonts/README.md)。フォント未取得でもswapで本文を先に表示し、失敗時は端末標準へ戻します。全フォントの先読みは行いません。

管理タブの大区分は `.management-section`、その他のアカウント欄は `.service-section` で「区切り線→上余白→番号付き見出し→短い説明→操作」を共有。線の上下28px・見出し下12pxを基準にし、実際の入力欄だけ白い面で区切ります。番号は分類の目印で、全項目を順に操作する指示ではありません。長い手順は `.tool-help` のdetailsで必要時に開き、保存前の警告/確認は既存controllerに残します。

承認待ち更新欄は「訂正と承認」の下へ。その他は「自分のアカウント→招待受取り→開発用の診断」の順にし、普段使わない診断を閉じておきます。親 `#staff-section` は両タブ共用のため囲わず、id/hidden/disabledは維持。表示を許可するためにCSSでhiddenを外してはいけません。

利用者向けは[管理画面の使い方](admin-guide.html)。操作できない[管理の表示見本](design/manager.html)・[その他の表示見本](design/more.html)は実HTMLから生成し、認証/保存機能や実社員データを持ちません。再現は `python scripts/build-workforce-design-preview.py`（repoルート）。見本はid表示の解除があるため現役ページとして流用しないでください。生成物を手編集せず、index.htmlとapp.cssを直して再生成します。

通信中の表示は[軽量なCSSのクルクル](LOADING.md)を使用。実pendingのaria-busyに同期し、追加の通信・アニメーション用タイマー・ライブラリは使いません。終了/エラー/timeout後は止め、状態の文字を残します。

現在の入口は[管理者/従業員の画面分離](ROLE-PAGES.md)を参照。管理タブは直接訂正・承認・従業員記録、本人の申請/記録は従業員側です。共通処理を複製せず、既存の権限検査と保存を維持します。

この資料は、所有者が後から自分で画面を調整するための入口です。対象はUI2の打刻・日別記録・訂正ページ。まず「何を変えたいか」から探し、対応するソースの番号付きコメントへ進んでください。

## 1. 何を優先して作ったか

**勤務中の人が、次に押す操作を短時間で見つけられること**を優先しています。装飾の完成形を固定する設計ではありません。

| 設計思想 | 一般化した概念 | このアプリでの使い方 |
|---|---|---|
| 目的ごとに置き場所を決める | Information architecture（情報設計） | 打刻・記録・管理・その他。ソースファイルの分類をそのままメニューにしない |
| 大事なものから読む | Visual hierarchy（視覚的な階層） | 勤務状態と打刻を大きく、予定・履歴を次に、診断は普段の画面から離す |
| 必要になった時に詳しくする | Progressive disclosure（段階的な開示） | 招待・診断は詳細欄、訂正は確認内容を見てから実行 |
| 一つの話題をまとめる | Grouping / proximity（まとまり・近接） | 一日分を一枚のカードにし、別の話題との間は余白を置く |
| 同じ意味を同じ見た目にする | Consistency / design tokens | 主操作、補助、注意、本文、補足を役割でそろえる |
| 表示と許可を分ける | Separation of concerns（責務分離） | CSSは見た目、layoutは移動、controller/GASは操作と認可 |

「管理タブへ移れた」ことと「管理者として実行できる」ことは別です。見た目の改造で権限を判断しないでください。
現在は起動時の署名付き確認後だけ管理タブを有効にし、それまではnativeのdisabledとaria-disabledで暗転します。layout.jsがdisabledを変更してよい対象はこのナビだけです。保存ボタンやフォームのdisabledは元のcontrollerが担当します。本人の操作を行うタブは権限確認を待たずに使えます。

## 2. 変更したい内容から探すMAP

中抜けの表示は`.session-list`、追加する訂正入力は`.extra-session`、承認待ちの表示はpending-approvals.jsのカードが担当します。名前/社員番号は一覧から読み取った文字をtextContentで表示します。氏名だけでなく社員番号と対象日も残し、同姓同名や別日の取り違えを防ぎます。カードの選択と承認の実行は一つの操作にまとめません。

| 変えたいこと | まず探す場所 | 波及する範囲・注意 |
|---|---|---|
| 全体の色 | app.cssの01、`:root`の変数 | ホーム・日別・訂正の3ページ。復旧/試験ページは別CSS |
| 主操作の色 | `--teal` / `--teal-dark` | ボタンとリンク、hoverを一緒に確認。停止の`--danger`とは分ける |
| カードの角丸 | `--radius` / `.record-item` | 共通値を使わない12px等の部品もある。全部が一括では変わらない |
| 文字の大きさ | `h1` / `.detail` / `.clock` / `.metric-grid strong` | 同じselectorの後方上書きを検索。ボタン/補足/値を全部同じ大きさにしない |
| 打刻ボタンの高さ・大きさ | `#punch-section .demo-actions button` | 実画面はこのID規則。見本用`.button.large`を変えても変わらない |
| カード内の余白 | `.card` / `.punch-card` / `.home-journal` | 親のpaddingと子のmarginを区別する |
| PCの最大幅 | 後方の`.app` / `.secondary-page main` | 現在はホーム1040px、専用ページ980px。行が長すぎないか確認 |
| スマホの1列配置 | 最後の`@media(max-width:799px)` | PC側の800px条件と境界を合わせる。狭めたPCにも同じ規則が効く |
| 下のナビの高さ | 後方の`.bottom-nav`と`.home-page main` | 本文末尾の余白も合わせ、最後のボタンがナビへ隠れないようにする |
| 画面の順番・名称 | index.htmlの5つのtab / layout.jsの`names` | 表示名だけならHTML。順番/追加はキー操作とaria属性も同期 |
| 日別カード内の順番 | attendance-journal.jsの`renderCards` | ホーム本日と日別ページが共有。表示項目の意味やnullを壊さない |
| 入力欄の見た目 | app.cssの入力規則 / `.secondary-page` | 確認前後のhidden/disabledを変更しない |
| 表示時計の形式 | shell.jsの`paint` / `.clock` | 表示だけ。打刻時刻は引き続きGASが決める |

`class`は見た目のまとまりを付ける名前です。`id`は特定の要素を一つ識別する名前で、既存JSから参照されています。見た目の整理だけなら、先にclassを使った調整を考えます。

## 3. CSSを読む時の基礎

```css
.card {
  padding:20px;
}
```

`.card`が「どの要素へ適用するか」を選ぶselector、`padding`が性質、`20px`が値です。paddingは枠の内側、marginは枠の外側の余白です。
このアプリの`box-sizing:border-box`では、指定した幅の内側にpaddingとborderを含めます。文字を大きくした時は高さを伸ばして収め、固定高さと`overflow:hidden`で説明を消さないでください。

```css
:root {
  --teal:#21635e;
}
.button.primary {
  background:var(--teal);
}
```

変数は「値に役割の名前を付ける仕組み」です。ボタンごとの色番号を一つずつ直すより、同じ役割を保ちやすくなります。すべての値が変数化されているわけではないため、反映しない部品はselectorを検索します。

**同じ部品への指定が複数ある場合は、詳細度と後に書いた順序が効きます。** 例えば`.metric-grid strong`の最終サイズは末尾の18pxです。前方の26pxだけを変えても、末尾の指定が優先されます。`#punch-out`のようなID指定はclass指定より強いので、後ろへ書くだけで変わらない場合もあります。
現在は見本由来の基本規則の後に、現役画面の調整を重ねています。番号13以降と同じselectorの全出現箇所を先に見てください。順番の入替えや重複の削除も見た目を変える可能性があります。

## 4. 小さな魔改造レシピ

### A. テーマ色を変える

1. `:root`の`--teal`と`--teal-dark`を探す。
2. 二つを同じ色系統で調整し、主操作とhoverの差を残す。
3. 白い文字、リンク、選択中のナビを3ページで確認する。
4. `--danger`や状態文まで同じ色へそろえない。色が見分けづらくても文言と状態で判断できるようにする。

### B. 打刻ボタンをもう少し押しやすくする

`#punch-section .demo-actions button`の`min-height:62px`や`font-size:19px`を調整します。例えば高さを68pxへ増やす場合、幅の狭い画面で「休憩を終了する」が折れても文字が切れないか確認します。
`min-height`は最低の高さです。`height`で固定すると文字拡大時に切れる場合があります。ボタンの有効/無効やクリックの保存処理を変更する必要はありません。

### C. カードの間を広くする

`.punch-grid`の`gap`、`.card`の`margin-bottom`、`.record-list`の`gap`から対象を選びます。全部へ同じ余白を足すと二重に広がります。カードの内側を広げたい場合は`padding`を変えます。
余白を増やした後は、スマホの最初の画面で状態と主操作が見つかるか、ページ末尾が固定ナビの下へ隠れないか確認します。

### D. 日別カードの見出しを変える

`renderCards`内の`record-head`と`record-times`を探します。文言や並びを変える場合も、日付・勤務状態・実績・予定の対応を保ちます。ホームも同じ関数を使うので両方確認してください。
「予定超過」は法定時間外ではありません。意味が違う名称へ変える場合は、表示だけでなく業務仕様の変更になります。未確定の`null`を0にすることもデザイン調整に含めません。

## 5. 変える前に知っておく境界

- **表示の非表示を解除しない**：`[hidden]`の規則、ボタンのhidden/disabledは業務状態と結び付いています。CSSで常に表示して問題を隠さないでください。
- **確認・取消を装飾扱いしない**：同意や二重送信抑止を省く変更は動作の変更です。打刻の確認はブラウザ標準confirmなので、CSSのdialog規則を変えても変わりません。
- **実画面と見本を区別する**：`.preview-tools`、`.width-tools`、`.phone`などは見本由来。公開HTMLで使う名前を検索してから触ります。prototypeのファイルだけを変えても公開画面は変わりません。
- **共有範囲を知る**：app.cssの削除は3ページの見た目へ、renderCardsの削除はホーム/日別へ、layout.jsの削除はタブ移動へ影響します。保存済み原簿は消えませんが、利用者が操作できなくなる場合があります。
- **長い文字と入力を試す**：日本語の長いラベル、社員番号、理由、200%の文字拡大、キーボードでの移動を確認します。小さい文字と薄い色だけで情報を詰め込まないでください。
- **秘密を見た目のサンプルに使わない**：実社員の氏名/勤怠/token/招待コードをCSSコメント・見本・公開スクリーンショットへ貼りません。

## 6. 変更してから公開するまで

1. まず1テーマだけ変更し、Gitの差分で対象と影響を確認します。今回と同じ説明だけの変更では、処理・CSS値を変えていないことも照合します。
2. 公開repoのルートで`node --test tests/*.mjs`を実行します。CSS先頭のコメント事故・変数未定義は`ui2-style.test.mjs`、タブは`layout.test.mjs`、カードは`attendance-journal.test.mjs`です。
3. private repoの連結用固定commit/hashとworkflowを同期します。CSS/HTMLの変更も固定対象なので、ハッシュ不一致を回避するためにcheckoutを勝手に巻き戻しません。
4. 公開する内容を確認してGitHub main→既存Pagesへ配布します。GAS手編集は不要です。CSS値や構造を変更した場合は3ページの`app.css?v=...`も同じ版へ更新し、古いキャッシュと区別します。
5. 390px程度の狭い幅とPC幅で、横にはみ出さないこと、操作ボタンが読めることを確認します。LINE本人での5タブ/状態確認も、模擬テストと分けて行います。

CSSをコピーするときは`/*`から`*/`までを一組で扱います。コメント内に`:root`等の語があっても、文字検索の最初の一致から切り出さないでください。UI2の初回公開ではこの事故で共通色が無効になりました。文字が白いのに背景色だけが消えた場合は、変数定義とCSSの読み込みを先に確認します。

## 7. 迷った時の順番

「どの画面か」→「どの部品か」→「CSSで変わる見た目か、JS/GASの意味か」→「共有先はどこか」の順に確認します。
変更の戻し方はGitHubの履歴から戻すことが基本です。動かないからとGASのコードを別に書き換えたり、保存済みデータを削除して合わせたりしません。

## シフトの専用導線

シフトを記録/管理から独立させ、5タブの3番目へ配置。管理者の作成入口はシフト内でも署名済み権限確認後だけ表示する。作成画面は下書き→希望確認→全体一覧（開閉）→受付設定→イベント→公開へ分け、上の短い作業リンクで移動できる。空の月暦31日分が入力欄を押し下げないよう、一覧を開閉式にした。HTMLの既存idとcontrollerの無効化/署名/再送を維持し、レイアウト変更で保存条件を代用しない。公開特記と非公開特記は別ラベル/別入力欄。変更時は両HTML・schedule.js・GAS Model/Service・公開漏れのテストを同期する。
